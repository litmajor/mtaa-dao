# AI layer integration

Three internal layers plus a set of "Elder" modules:

| Layer | Code | Role |
| --- | --- | --- |
| **Morio** | `server/agents/morio/**`, `/api/morio/*` | Conversational entry point; the only layer with HTTP routes |
| **Nuru** | `server/core/nuru/**` (`export const nuru = new NuruCore()`) | Reasoning: intent classification, context, analytics, risk |
| **Kwetu** | `server/core/kwetu/**`, `server/services/kwetuService.ts` | Service/execution layer over treasury, governance, community |
| **Elders** | `server/core/elders/{scry,kaizen,lumen,coordinator}` | Long-running monitoring/optimisation/ethics modules |

They talk over the in-process [message bus](/developer/agent-communication), not over HTTP.
Only Morio is reachable from outside the server.

<Callout type="warning">
  **"AI" here is mostly deterministic code.** Nuru's intent classifier is a table of regular
  expressions with confidence computed as `match.length / message.length` — not a model. The
  only genuine LLM path is Morio's provider, and the committed configuration selects
  `ollama`, which the factory does not recognise, so it falls back to the **mock** provider.
  Do not present Morio output to users as authoritative analysis without changing that config.
</Callout>

## Request path

```text
client → POST /api/morio/chat            (isAuthenticated + authenticateToken)
       → Morio                            builds context, may call the LLM provider
       → messageBus USER_QUERY/ANALYSIS_REQUEST
       → Nuru.understand()/analyze()      regex intent + analyzers + risk assessment
       → Kwetu (read-only services)       treasury/governance/community lookups
       → response back over correlationId
```

Anything with a financial effect stops before execution: Morio returns a proposed action and
the client must call `POST /api/morio/confirm-action`.

## Nuru

`NuruCore` subscribes to `ANALYSIS_REQUEST`, `USER_QUERY`, `HEALTH_CHECK` and
`RISK_ASSESSMENT` through an `AgentCommunicator('NURU')` and answers on the message's
`correlationId`.

Composed of:

- `nlu/intent_classifier.ts` — regex patterns per intent, priority-ordered
- `reasoning/context_manager.ts` — enriches user context with the classified intent
- `analytics/` — `financial_analyzer`, `governance_analyzer`, `community_analyzer`, plus
  `dao_analyzer`, `vault_analyzer`, `wallet_analyzer`, `contribution_analyzer`
- `ethics/risk_assessor.ts` — proposal/DAO risk assessment
- `market_integration.ts` — `MarketAwareIntentAnalyzer`, `CrossAssetRiskAnalyzer`, wired to
  the symbol universe and market data

`understand()` extracts mentioned assets from the intent's entities and, when there are any,
enriches with market context — failing **soft**: a market-data error is logged and the answer
continues without market context.

<Callout type="info">
  Nuru is not exposed over HTTP. To reach it from a route you publish a message on the bus and
  await the response, with the bus's 5-second default request timeout.
</Callout>

## Kwetu

`KwetuCore.execute({ service, method, params })` dispatches to four services:

| Service | Methods |
| --- | --- |
| `treasury` | `getBalance`, `getTransactions`, `getTreasuryMetrics` |
| `governance` | `getProposals`, `getProposalById`, `getVotingPower` |
| `community` | `getMemberCount`, `getMemberStats`, `getEngagementMetrics` |
| `execution` | `planExecution`, `executeOperation`, `monitorExecution`, `analyzeHealth` |

Unknown service or method throws. The first three are read-only; only `execution` mutates.

`server/services/kwetuService.ts` is the guarded entry point for anything the AI proposed:

```ts
safeExecuteAction(pendingActionToken, executingUserId)
```

It consumes a single-use pending-action token, verifies the caller is a member of the target
DAO (throws otherwise), then executes exactly one of `create_proposal`, `cast_vote`,
`open_withdrawal`/`withdraw` — anything else throws `Unsupported action type`. Both success
and failure write an audit log carrying the actor, DAO, action type, payload and token.

<Callout type="warning">
  Membership is the only authorization check in `safeExecuteAction` — it does not check the
  member's *role*, unlike the proposal route, which requires `admin`/`proposer`/`elder`/`creator`.
  A plain member could create a proposal through the AI path. Security gap / recommended control.
</Callout>

## Elders

Four modules under `server/core/elders/`:

| Module | Class | Purpose |
| --- | --- | --- |
| `scry` | `EldScryElder` | DAO surveillance: `monitorDAO(daoId, activities)`, per-DAO metrics, status |
| `kaizen` | — | Optimisation |
| `lumen` | `EldLumenElder` (`eldLumen` singleton) | Ethics/oversight, configurable via `EldLumenConfig` |
| `coordinator` | — | Its own `message-bus.ts`, separate from the agent-framework bus |

HTTP entry points: `/api/elders/*`, `/api/morio/elder-insights/elder-insights`,
`/api/morio/data-hub/elders/overview`, and admin routes under `server/routes/admin/`.
Persistence lives in `server/db/schema/agents-elders*.ts` with migrations `005`/`006`.

## Building on the AI layer

Practical guidance given the above:

1. Call Morio over HTTP; do not attempt to reach Nuru or Kwetu directly from a client.
2. Never auto-execute a Morio suggestion — go through `confirm-action` and
   `safeExecuteAction`, which is where the token, membership check and audit log live.
3. Treat confidence scores as heuristics (`match.length / message.length`), not probabilities.
4. Configure a real LLM provider (`openai`) before relying on generated text.
5. Expect single-process behaviour: bus state, sessions and elder state do not survive a
   restart or span replicas.
