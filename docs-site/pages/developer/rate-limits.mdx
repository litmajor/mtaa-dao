# Rate limits

Source of truth: `server/middleware/rateLimiter.ts`, `rateLimitConfig.ts`,
`rateLimiting.ts`, `capitalFlowRateLimits.ts`, `phase2RateLimits.ts`.

<Callout type="warning">
  **This page replaced an earlier version** claiming commercial tiers ("Free 100/min, Pro
  $99/mo 1,000/min, Enterprise custom") and burst/SLA guarantees. No tiered plan is
  enforced anywhere in the code. Limits are per-operation and per-route.
</Callout>

## Response contract

Limiters built on `rateLimitMiddleware` (`rateLimitConfig.ts`) set:

| Header | Meaning |
| --- | --- |
| `X-RateLimit-Limit` | Configured maximum for the window |
| `X-RateLimit-Remaining` | Remaining requests in the current window |
| `Retry-After` | Seconds to wait — only on a `429` |

Exceeding a limit returns `429` with
`{ "error": "Too many requests", "retryAfter": <seconds>, "message": "..." }`.

Windows are **fixed**, not sliding: the Redis key is
`rl:<key>:<floor(now / windowSeconds)>`, so the counter resets on a wall-clock boundary and
a client can spend a full window's budget on each side of that boundary.

<Callout type="warning">
  **Security Gap / Recommended Control.** `checkRateLimit` **fails open**: if Redis is
  unavailable or errors, the request is allowed and only a log line is emitted. A Redis
  outage silently removes rate limiting from withdrawals, deposits, order execution and
  proposal operations. Consider failing closed for financial operations.
</Callout>

## Capital flow

`rateLimitConfig.ts` limits are the ones actually wired into the gateway rails
(`server/routes/v1/wallets/rails/gateway.ts`):

| Operation | Limit | Window | Scope |
| --- | --- | --- | --- |
| `POST /api/v1/wallets/rails/gateway/deposit` | 20 | 1 hour | user |
| `POST /api/v1/wallets/rails/gateway/withdraw` | 10 | 1 hour | user |
| Withdrawals over $10,000 (`applyAdaptiveRateLimit`) | 3 | 24 hours | user |

<Callout type="info">
  Two further configurations exist but are **not enforced**: `capitalFlowRateLimits`
  (deposits 50/day, 20/hour, 5/10min; withdrawals 5/day, 3/hour, 1/10min) is consumed only
  by `capitalFlowMiddleware.ts`, which no route imports, and `phase2RateLimits` is a
  configuration object with a commented-out usage example. Treat their numbers as
  **PLANNED**, not as the limits you will hit. The enforced withdrawal limit is 10/hour.
</Callout>

  (`server/routes.ts:449`), as a `307` rewrite to `/api/v1/daos/...` (`server/routes.ts:511`),

</Callout>

## Trading (Yuki v1)

The mounted trading surface is `/api/v1/yuki` (`server/routes/v1/yuki/`). Limits are
defined per sub-router:

| Operation | Limit | Window | Where |
| --- | --- | --- | --- |
| Algo order writes (`POST /algo/twap`, `PATCH`/`DELETE /algo/orders/:id`) | 20 | 1 min | `algo.ts` |
| Algo order reads (`GET /algo/orders`) | 100 | 1 min | `algo.ts` |
| Bridge transfer | 5 | 1 min | `bridge.ts`, keyed per user |
| Bridge swap | 10 | 1 min | `bridge.ts` |
| Bridge governance ops | 20 | 1 min | `bridge.ts` |
| Bridge quote | 30 | 1 min | `bridge.ts` |
| Bridge analytics | 50 | 1 min | `bridge.ts` |

<Callout type="info">
  `server/routes/yuki.ts` — the legacy trading router carrying `yukiSwapLimiter` (20/min),
  `yukiBridgeLimiter` (10/min), `yukiFlashLoanLimiter` (5/min) and `yukiBacktestLimiter`
  (3/min) — is **not mounted** by `server/routes.ts` or `server/index.ts`, so those limits
  are not in force. `orderExecutionLimits` (100/min) and `agentLimiter` (10/min) are
  likewise defined but not attached to any mounted route.
</Callout>

## Global limits

| Configuration | Value | Status |
| --- | --- | --- |
| `riskAssessmentLimits` | 50 / hour, key `risk_assessment_global` | Available |
| `marketDataLimits` | 1,000 / min, key `market_data_global` | Available |
| `globalRateLimiter` (`rateLimiting.ts`) | 100 / window (5,000 in development), with a long static-asset exemption list | **Defined but not mounted** — referenced only by tests |
| `RATE_LIMIT_WINDOW_MS` / `RATE_LIMIT_MAX_REQUESTS` env (default 900,000 ms / 100) | Parsed into `rateLimitConfig` in `shared/config.ts` | **Not consumed by any middleware** |

<Callout type="warning">
  **Security Gap / Recommended Control.** There is no application-wide default rate limit
  in force. Protection is opt-in per route, so any endpoint whose author did not attach a
  limiter is unlimited. The two mechanisms intended to provide a floor — `globalRateLimiter`
  and the `RATE_LIMIT_*` environment settings — are both dead code paths. Mounting one of
  them would give every endpoint a baseline.
</Callout>
