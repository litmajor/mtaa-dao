# API reference

This page describes the conventions every endpoint shares. The endpoint list itself is
**generated from the Express route graph** — see [API endpoints](/reference/api), which
covers all 1,206 statically resolvable routes across seven surfaces.

<Callout type="warning">
  The interactive explorer below is a curated illustration, not the endpoint inventory. Where
  it disagrees with [/reference/api](/reference/api), the generated reference is correct.
</Callout>

## Base URL

From `server/config/swagger.ts`, the servers the API declares for itself:

| Environment | Base URL |
| --- | --- |
| Development | `http://localhost:5000/api` |
| Staging | `https://staging-api.mtaadao.com/api` |
| Production | `https://api.mtaadao.com/api` |

Everything is mounted under the `/api` prefix (plus `/walletapi`, `/health` and `/metrics`
outside it). There is **no `/v1` root**: versioning appears one level down, as
`/api/v1/...`, and unversioned `/api/...` routes coexist with it. Behind Docker, Nginx
proxies `/api/` to the API container — see [Operations](/operations).

Swagger UI is served at `/api-docs` when the app boots successfully.

## Authentication

Cookie-based JWT by default (`access_token`), with `Authorization: Bearer <jwt>` accepted as
a fallback and a double-submit `X-CSRF-Token` required on non-safe methods. The Swagger
document also declares an `X-API-Key` scheme.

<Callout type="error">
  **`X-API-Key` is not enforced.** API-key tables exist in the schema, but no mounted
  middleware authenticates a request by API key. Only the JWT paths work today. Full detail
  in [Authentication](/developer/authentication).
</Callout>

## Response envelopes

Success shapes are **not uniform** across the codebase — many handlers return a bare object
or array, others wrap in `{ success: true, data }`. Check the specific endpoint rather than
assuming an envelope.

Errors that reach the central handler (`server/middleware/errorHandler.ts`) are uniform:

```json
{
  "success": false,
  "error": {
    "message": "Treasury balance is too low",
    "timestamp": "2026-08-13T10:24:00.000Z",
    "path": "/api/v1/daos/abc/treasury/transfer",
    "method": "POST",
    "code": "APP_ERROR",
    "statusCode": 400
  }
}
```

`error.stack` is added in development only. Zod validation failures add `error.details` with
the raw issue list:

```json
{
  "success": false,
  "error": {
    "message": "Validation failed",
    "code": "VALIDATION_ERROR",
    "statusCode": 400,
    "timestamp": "2026-08-13T10:24:00.000Z",
    "path": "/api/v1/daos",
    "method": "POST",
    "details": [{ "path": ["name"], "message": "Required", "code": "invalid_type" }]
  }
}
```

## Error codes

Codes emitted by the `AppError` subclasses in `server/middleware/errorHandler.ts`:

| Code | Status | Raised when |
| --- | --- | --- |
| `VALIDATION_ERROR` | 400 | A Zod schema rejects the request |
| `INVALID_ID` | 400 | `CastError` — malformed identifier |
| `RATE_LIMIT_EXCEEDED` | 429 | A mounted limiter rejects the request |
| `DATABASE_ERROR` | 500 | Database operation failed |
| `EXTERNAL_SERVICE_ERROR` | 502 | An upstream service failed; message is prefixed with the service name |
| `APP_ERROR` | varies | An `AppError` thrown without an explicit code |
| `INTERNAL_ERROR` | 500 | Unclassified error |

Auth failures are returned directly by the auth middleware rather than the error handler, so
they carry `{ success: false, error: { message } }` without a `code` — see
[Authentication](/developer/authentication).

## Rate limiting

Rate limiting is **opt-in per route**, not global. Limits, headers and the Redis fail-open
behaviour are documented in [Rate limits](/developer/rate-limits).

## Deprecated routes

Some legacy paths redirect or return `410 Gone` with `Sunset` headers. See
[Deprecated & removed APIs](/reference/deprecated).
